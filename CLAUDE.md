# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MedSafe — a cross-hospital polypharmacy (drug-drug interaction) warning system built as a **static, no-build-step frontend** (plain HTML + Vue 3 via CDN + Tailwind CDN + ECharts) backed by **Firebase Authentication + Cloud Firestore**, with a real **HAPI FHIR R4** integration for cross-hospital data exchange. Four role-based portals: patient (`patient.html`), doctor (`dashboard.html`), admin (`admin.html`), insurance underwriter (`insurance.html`).

There is no bundler, no transpiler, no npm build. Every `.html` page loads `js/*.js` files directly as global-scope scripts (`window.DbService`, `window.DdiEngine`, `window.FhirClient`, `window.auth`, `window.db`, etc.) — not ES modules on the frontend. `package.json`'s `"type": "module"` and the `tests/*.mjs` files apply only to the Node-based test suite, not the app itself.

**The Firestore security rules (`firestore.rules`) are the single real access-control boundary of this system.** Anyone can download the entire frontend (it's static and public), so every authorization decision must be enforced in rules, not in JS. Treat `firestore.rules` as the most security-critical file in the repo — read its extensive inline comments before touching it; they document *why* each clause exists, including specific vulnerabilities that were found and fixed (referenced as `P0-x`/`P1-x`/`S-x`/`H-x` in comments, from an internal adversarial audit).

## Commands

```bash
npm test               # runs all suites below, in order
npm run test:catalog   # tests/drug-catalog.test.mjs    — drug identity resolution (pure Node, no emulator)
npm run test:ddi       # tests/ddi-engine.test.mjs       — DDI matching engine (pure Node, no emulator)
npm run test:fhir      # tests/fhir-client.test.mjs      — FHIR client layer (pure Node, no emulator)
npm run test:nlu       # tests/line-nlu.test.mjs         — LINE 服藥回報的 LLM 語意理解 (pure Node, no emulator)
npm run test:webhook   # tests/line-webhook.test.mjs     — LINE webhook signature/idempotency/intent routing (pure Node, no emulator)
npm run test:richmenu  # tests/line-richmenu.test.mjs    — LINE Rich Menu layout/setup (pure Node, no emulator)
npm run test:exchange  # tests/line-exchange.test.mjs    — LIFF ID Token → Custom Token bridge validation (pure Node, no emulator)
npm run test:rules     # tests/firestore-rules.test.mjs  — requires `firebase emulators:exec --only firestore`
```

- `test:rules` spins up the Firestore emulator itself (via `firebase emulators:exec`) and reads `firestore.rules` directly from disk — it always tests the exact file that would be deployed. Requires the Firebase CLI to be installed and buildable emulator binaries (Java).
- To run a single test file directly: `node tests/ddi-engine.test.mjs` (these are plain assertion scripts, not a test-runner framework — no `--grep`/filtering support; edit the file or read its output to isolate a case).
- **Any change to `firestore.rules` or to drug/DDI identity logic (`js/drug-catalog.js`, `js/ddi-engine.js`, `js/ddi-rules-ddinter.js`) must be followed by the corresponding test suite before considering the change done.**
- No lint/typecheck config exists in this repo — don't invent one.
- Local run: the app **must** be served over HTTP, not opened via `file://` (Firebase Auth rejects the `file://` origin): `python -m http.server 8000` or `npx serve .`, then visit `http://localhost:8000` → redirects to `login.html`.

## Architecture

### Identity & auth model
- Users log in with a plain `username` + password. The frontend synthesizes a fake email (`username@medsafe.local`, see `toAuthEmail()` in `js/auth.js`) and calls Firebase Auth — Firebase Auth itself is only used as a password/session mechanism, not as the identity source of truth.
- `user_roles/{uid}` in Firestore is the **sole trusted identity index** (role + status + username), keyed by Firebase Auth `uid`. Every other collection's rule derives authorization from this document via `profile()` in `firestore.rules`, never from `localStorage` or client-declared role.
- `js/auth.js`'s `verifyRole()` re-derives the verified identity from Firestore on every page load and only mounts the Vue app after that succeeds (`mountWhenAuthorized`) — there is deliberately no "render UI optimistically, redirect if unauthorized" window.
- Three distinct failure modes are handled differently and must stay distinct when modifying auth code: **denied** (not logged in / disabled account → sign out + wipe local state + redirect to login), **wrong room** (valid session, wrong role for this page → redirect to own home, do NOT sign out or wipe data), and **infra failure** (offline/timeout → show a retryable screen, do NOT sign out or wipe data). Conflating these has previously destroyed unsynced user data on transient network errors.
- `js/firebase-config.js` sets up a **second** Firebase Auth app instance (`window.secondaryAuth`) purely so that admin's "create user" flow doesn't hijack the admin's own logged-in session when calling `createUserWithEmailAndPassword`.
- Firebase config values (`apiKey` etc.) are intentionally public in `js/firebase-config.js` — this is a public-client web app; security is enforced entirely by Firestore rules, not by hiding config.

### Access-control patterns to know before editing `firestore.rules`
- **`{a}__{b}` composite document IDs** are used throughout (`care_relations`, `consents`, `break_glass`) so rules can do O(1) `get()`/`exists()` lookups instead of queries (Security Rules can't query collections, only read known paths). When adding a new relationship-gated collection, follow this pattern rather than introducing a queryable index.
- **Reading a not-yet-existing document** (to decide create-vs-update client-side) needs special-cased `resource == null` handling in the rule, scoped narrowly so existence itself doesn't become an oracle (see `ridNamesMe()` and its long comment for the reasoning about why a naive `resource == null` allow is a leak).
- **`get()` doesn't exist means "not found"**; a bare boolean leak on relationship existence (e.g., "is this patient assigned to this doctor") is treated as a privacy leak in this codebase (reveals the fact of a care relationship) — new rules should preserve that indistinguishability where relevant.
- **Write-once fields** (`fhirPseudonym`, `profile.nationalId`) use a "set once, immutable after" pattern rather than a general-purpose update, to prevent identity/pseudonym reassignment attacks.
- **Accountable/attested fields** (`nationalIdVerifiedBy/At`, `audit_logs.actor`, `patient_summaries.attestedBy`, prescriptions' `safetyCheck`) always require the writer to name themselves as `profile().username` (cross-checked against `token.email` via `ownsUsername()`), and timestamps must equal `request.time` server-side — never client-supplied. When adding a new "who did this / when" field, follow this exact pattern.
- **`get, list` are split** where enumeration would be a privacy escalation even though single-document lookup is fine (`patient_index`: `get` allowed, `list` denied) — don't collapse these back into a single `read` grant.
- **Break-glass / emergency access** (`break_glass` collection) is a deliberate, audited self-authorization escape hatch for doctors with no care relationship (ER scenarios). It requires a named reason (≥10 chars), server-set timestamps, and a 4-hour hard expiry, and records can never be updated/deleted (only superseded by a fresh declaration). This is intentional — do not "fix" it into a stricter/blocking model without understanding the availability-vs-safety tradeoff documented at that rule.
- The rules file records several **previously-shipped vulnerabilities and their fixes inline** (grep for `對抗性稽核`, `曾經的漏洞`, `S-1`, `S-2`, `H-2` through `H-7`, `P0-`, `P1-`). Before changing a rule, read its comment block fully — it usually explains a regression that already happened once.
- Known, deliberate, *undocumented-to-users-but-documented-in-code* limitations of the rules layer (don't try to "fix" these without discussing scope first): no global uniqueness enforcement for `fhirPseudonym` or `nationalId` beyond format; audit logs can't guarantee every action is logged (client must choose to write them); consent/patient_summary data is patient-attested, not system-verified. See `DEPLOY_CHECKLIST.md` §5 for the full list of known tradeoffs and how to explain them.

### DDI (drug-drug interaction) engine
- `js/drug-catalog.js` + `js/ddi-rules-ddinter.js` (data imported from `DDINTER2/*.csv` via `tools/import-ddinter.mjs`) provide drug identity resolution; `js/ddi-engine.js` performs matching by **ATC code**, not by drug-name string equality (name matching was the original bug — cross-hospital name variants like "Warfarin Sodium" vs "Warfarin" didn't match).
- The engine checks **all pairs among existing medications**, not just "new drug vs. existing drugs" — a patient's existing regimen can itself contain an unflagged interaction.
- Severity has a distinct `unknown` rank *below* `minor`, not folded into `moderate` — an interaction from DDInter's `Unknown` severity data must never render or sort as if it were a confirmed moderate/major interaction. Preserve this distinction in any severity-related change.
- "No interaction found" and "cannot be evaluated" (unmapped/compound drug) are different states and must never be collapsed into a single "safe" result — this exact conflation was a fixed audit finding (P0-3/P1-12).

### Prescription safety gate
- `firestore.rules`'s `patient_data` collection enforces that any *newly appended* medication must carry a `safetyCheck` map (`verdict`, `checkedAt`, `by`), and if `verdict == 'risk'`, a named `overrideReason` (≥4 chars) is mandatory. This is enforced at the data layer specifically because a UI-only "must check before prescribing" gate is trivially bypassable by calling the Firestore SDK directly. When touching prescription-writing code paths, preserve this invariant rather than relying on frontend flow control.
- Prescriptions carry an optional, **display-only** `durationDays` (nullable — null means indefinite/long-term) and `prescribedAt` (local date string via `DbService.adherence.dayKey()`, set at prescribe time). Neither is rules-enforced or triggers any automatic behavior — course expiry is shown to the doctor as a visual cue only ("已過，請評估是否停用"); the system never auto-discontinues a medication. That's a deliberate clinical-safety choice, not a missing feature — see `linebot.md`'s parallel reasoning about not letting a scheduler make medical judgment calls.
- **Discontinuing a medication is a separate collection, not a field edit on `medications[]`.** Rules cannot iterate an array or locate an element by `id` — the `addedMed()` trick that gates *new* prescriptions only works because a push is always the *last* array element; discontinuing an arbitrary *existing* entry has no such guarantee. So `medication_discontinuations/{patient}__{medId}` is a `create`-only collection (mirrors `care_relations`/`break_glass`'s composite-ID, accountable-record shape): `discontinuedBy == profile().username` + `ownsUsername()`, `discontinuedAt == request.time`, `reason` ≥4 chars, and the doc key must equal `patient + '__' + medId` (constructed and compared, never parsed apart — same reasoning as `ridStartsWithMe()`, since usernames may contain `_`). `update`/`delete` are always `false`. A medication's "currently active" status is therefore *derived*, never stored on `patient_data` itself: `DbService.getMedicationDiscontinuations(username)` returns a `{medId: record}` map that callers filter `medications[]` against (see `currentMeds`/`allMedsForDisplay` in `dashboard.html`, `medications`/`allMedications` in `patient.html`). Only doctors with an active care relation (or admin) can create one — **note this collection does not carry the legacy `assignedDoctor` fallback that `patient_data` still has**, so a pre-care-relation doctor won't see discontinuation records for their older patients until that patient also has a `care_relations` entry.
- `DbService.discontinueMedication()` also strips the matching entry out of `reminders[]` in the same batched write (text-matched as `'服用' + <canonical zh name>`, splitting/rejoining `、`-merged slots) — a stopped drug must not keep prompting the patient to take it. Known limitation, accepted deliberately: this reuses `reminders[]`'s existing text-based merge (not `medId`-linked), so two active prescriptions that happen to share an exact display name will have both wiped by discontinuing either one.

### Outpatient schedules & queue-number booking

- **The patient never picks a doctor.** Booking always targets the patient's existing doctor (`assignedDoctor` on the record, overridden by the most recent active appointment) — letting a patient name any account would be letting them decide who may read their own chart. `doctor_schedules` is therefore `get`-only, `list` denied (the `patient_index` precedent); `DbService.schedules` deliberately has no `listAll()`. A patient with no doctor yet, or whose doctor has published no hours, falls through to the legacy account-based booking — that first booking is what establishes the relationship.
- A doctor's clinic hours live in **`doctor_schedules/{doctorUsername}`** — a new collection, deliberately *not* `doctor_data`, which is a single shared `doctor_data/main` any doctor can overwrite. Shape: `weekly` keyed `'0'`(Sun)–`'6'`(Sat), each a map of the **three fixed session ids `am`/`pm`/`night`** → `{start, end, capacity}`; plus `exceptions` keyed `'YYYY-MM-DD'` → `{closed: true}` (停診) or `{sessions: {...}}` (加診). Sessions are a fixed-key map rather than an array because **security rules have no loops** — `map.get(k, default)` is the only O(1) lookup available; an array of sessions could not be validated at all.
- **Weekday is derived inside the rules** (`dowOf()` → `timestamp.date(...).dayOfWeek() % 7`, aligned to JS `getDay()`), never accepted from the client. A client-declared `dow` would let a patient book into a closed weekday just by lying about it.
- `firestore.rules`'s `sessionSpec()`/`sessionIsOpen()` and `js/db-service.js`'s `DbService.schedules.sessionFor()` implement **the same exceptions-override-weekly logic and must be changed together**. When they diverge, the UI offers a slot the rules then reject — the patient sees a button that does nothing.
- **`appointments` now has three mutually exclusive `create` paths**: (A) legacy free-text booking, gated on `!hasSchedule(doctor)` so today's behaviour is preserved *only* until a doctor publishes hours — after that the queue is the only way in; (B) queue booking, whose document ID is `{doctor}__{dateKey}__{session}__{seq}`; (C) the doctor's counter check-in, still an auto ID with no `seq`. A and B cannot both apply, so B is not bypassable via A.
- **`appointment_counters/{doctor}__{dateKey}__{session}`** exists because a patient can only read their *own* appointments (correctly), and therefore cannot know what number to take. It leaks the head-count, never who — the same number a waiting-room display shows. Rules on the counter and on the appointment **each `getAfter()` the other**: a counter bump with no matching appointment is denied (otherwise anyone could inflate any doctor's session to full), and an appointment with no counter bump is denied (otherwise two patients could both be number 1). Both writes must therefore be in one transaction — `DbService.appointments.bookQueued()`.
- **Numbers never shift.** Cancelling sets `status: 'cancelled'` and leaves a gap; the counter never decreases. Renumbering would silently pull forward a patient who has already left home. This also keeps the composite document ID permanently unique.
- **`scheduledAt` is a derived display value, not the authoritative fact.** Rules can validate `dateKey`/`session`/`seq` and the capacity, but cannot parse `'09:00'` to do time arithmetic, so the estimated time is unverifiable. Display code recomputes from `dateKey` + `seq` + the doctor's *current* schedule (`apptQueueText()` in `patient.html`) rather than trusting the stored timestamp.
- Capacity × `avgMinutes` may exceed the session length; the doctor UI **warns and still saves** (`scheduleWarnings` in `dashboard.html`) because clinics really do run over, and the patient-side estimate is shown honestly rather than clamped to the session end.

### Safety score (`用藥安全參考分數`)

- **One implementation only.** `DbService.safetyScoreBreakdown()` is the single scorer; every caller feeds it through `scoreInputFromAnalysis(DdiEngine.analyze(...))`. `dashboard.html` used to translate engine severities to Chinese labels itself with a *different* mapping (`major` → −20 there, −35 in `db-service`), so the same patient scored 80 on the doctor's screen and 65 on their own phone. No page may re-interpret `severity`.
- Weights (100 base; −35 contraindicated/major, −20 moderate, −8 minor/ungraded, −10 for ≥5 drugs, floored at 0) are **product constants, not a published pharmacological scale**. The UI must keep calling it a 參考分數, keep the disclaimer, and keep the expandable "這個分數怎麼來的" breakdown — an unexplained number in a medical app gets over-read.
- **Four states, never collapsed**: `no-medications`, `not-assessed` (engine never ran — an empty stored `ddiAlerts` array still means this, since nothing writes that field automatically), `all-unevaluable` (every drug unmappable — returns `null`, not 100 with a footnote), and `scored`. `scoreInputFromAnalysis` sets `assessed: true` so "engine ran and found nothing" scores 100 with a "查無記載 ≠ 安全" caveat instead of reporting 尚未評估 — that bug had the score circle contradicting the health summary directly beside it. `ungraded` findings (recorded but severity-unlabelled) are counted at the minor weight; previously they were dropped entirely, which told the user they did not exist.

### FHIR integration (`js/fhir-client.js`)
- Central `FhirClient` object: 12s timeout via `AbortController` (public HAPI sandbox is often slow/unresponsive), configurable base URL (read from `admin_data` settings, default `https://hapi.fhir.org/baseR4`), HTTPS-only.
- `isUnprotected()` is the flag actual UI warnings key off — it is **not** simply "is this hapi.fhir.org" (that was a fixed bug: warnings disappeared when pointed at a self-hosted-but-still-unauthenticated server). It defaults to "unprotected" unless an admin has explicitly declared `fhirAccessControlled` in settings; that declaration is an operator attestation, not something the client verifies.
- No API key / auth header is sent by design — a pure static frontend cannot hold a secret from its own users; anything stored in `admin_data` is readable by every authenticated user per the rules above. A real protected FHIR backend requires a server-side proxy (explicitly deferred, see file header "Phase 6" notes).
- Patient data sent to the public FHIR sandbox is pseudonymized: random `fhirPseudonym` per patient (not derived from username — a derived/hashed pseudonym would be reversible offline since the algorithm is public and the username space is tiny), blurred birth year (5-year bucket), no real name. This is explicitly documented as pseudonymization, not anonymization (medication + dosage combinations remain quasi-identifying).

### Chat / notifications
- `js/chatStore.js` + `js/notify.js` (localStorage/`storage`-event based) originally held doctor-patient chat entirely client-side; this was migrated to Firestore's `conversations/{patientUsername}/messages` (see rules section and `P1-4` comments) because chat is legally part of the medical record in Taiwan and can't live only in browser storage. Don't reintroduce localStorage as the source of truth for chat content — it's fine only as an ephemeral read/unread-count cache.

### National ID (身分證字號) handling
- `js/utils.js`'s `validateNationalId()` implements the Taiwan national-ID / new resident UI checksum algorithm (2nd digit `1`/`2` for citizens, `8`/`9` for the newer resident UI format — both share the same checksum). It runs client-side only and is deliberately **not** used for duplicate-registration lookups server-side — see the long comment there explaining why building a lookup index of hashed IDs in a public-source frontend is itself a privacy risk (offline rainbow-table feasible in ~69s against the ~52M valid ID space).
- Verification of a national ID (`nationalIdVerifiedBy/At` in `patient_data`) is a separate, staff-only attestation step from the patient's own self-reported entry — see `firestore.rules`'s `verificationIsAccountable()`. Note the documented regression it guards against: naively requiring `nationalIdVerifiedAt == request.time` on every write (not just when the verification fields actually change) made a verified patient's whole record permanently read-only, since any unrelated later write would fail that equality. Any change to write-once/attestation-style rules should consider this "unrelated field touches the same equality check" failure mode.

### Cloud Functions / LINE integration (`functions/`) — the second trust boundary
- `functions/` is the project's **first and only server-side component**, added solely because LINE's Channel Secret / Access Token are secrets and a static frontend cannot hold one (the same principle that caused the self-hosted FHIR proxy to be deleted). It runs in **`asia-east1`** — the Firestore database's location; Firestore triggers must match it, and the other functions follow for latency.
- It uses the **Admin SDK, which bypasses `firestore.rules`**. This is a deliberate second trust boundary, not a hole, and it is kept deliberately narrow — only: redeeming link codes, writing `line_bindings`/`line_users`, reading `reminders`/`medications` to build a push, and writing `adherenceLog` from a LINE postback. **Any path that reads a medical record in order to display it to a person must NOT use the Admin SDK** — it goes through a LIFF-issued Firebase Custom Token so the rules apply unchanged. Don't "simplify" a display path onto the Admin SDK.
- Four collections (`line_link_codes`, `line_bindings`, `line_users`, `line_push_log`) are closed to every client in the rules; the only reader/writer is `functions/src/bindings.js`. The one exception is a patient reading their own `line_bindings/{username}` to render "已綁定".
- **LIFF identity bridge (`functions/src/exchange.js`, `lineExchangeToken`)** is the mechanism that keeps the "no Admin SDK on display paths" rule practical: it verifies a LINE ID Token against LINE's `/oauth2/v2.1/verify`, checks the response's `aud` equals our own `LINE_LOGIN_CHANNEL_ID` (a non-secret param, like `LINE_BASIC_ID` — a LINE Login channel ID is public the same way an OAuth `client_id` is), looks up the `sub` (lineUserId) in `line_users`, and mints a Firebase Custom Token for the bound `uid`. Frontend half is `js/liff-bridge.js` (only activates on `?liff=1`, gated so normal username/password login never loads the LIFF SDK) + `js/line-liff-config.js` (`window.LIFF_ID`, also non-secret — it's visible in the browser address bar). Once `signInWithCustomToken` succeeds, the page is a normal authenticated session and `firestore.rules` applies unchanged — nothing downstream needs to know the login came from LINE. `extractLineUserId()` in `exchange.js` is a pure function (aud/sub validation) covered by `tests/line-exchange.test.mjs` for the same reason `verifySignature()` in `line-api.js` is: get the trust check wrong here and the whole bridge is a hole. `LINE_LOGIN_CHANNEL_ID` defaults to empty, which makes the function refuse cleanly (`failed-precondition`) rather than fail deploy — safe to deploy before the LINE Login channel + LIFF app exist.
- **Link codes are generated server-side, never by the client.** An earlier design let the patient write `line_link_codes/{code}` themselves with rules checking only `username` — but the document also carries a `uid` (needed for the Custom Token), and rules cannot verify it (`user_roles` is keyed by uid; rules can't reverse-look-up from a username — the same limitation noted at `appointments`). A patient could write `{username: self, uid: victim}` and take over the victim's account. Client-chosen document IDs were separately brute-forceable. Keep code generation in `lineCreateLinkCode`.
- `functions/vendor/` is a **generated copy** of `js/drug-catalog.js`, `js/ddinter-drugs.js`, `js/ddi-engine.js`, `js/ddi-rules-ddinter.js`, produced by `functions/sync-vendor.js` as a `predeploy` hook and git-ignored. Functions deploys only package `functions/`, so `require('../js/…')` would work locally and fail in the cloud. Never hand-edit `vendor/`, and never let a second DDI implementation exist — "doctor's screen says there's an interaction, LINE says there isn't" is the one failure this system cannot afford.
- **Timezone**: Functions run in UTC. `functions/src/taipei-time.js` reproduces `js/db-service.js`'s local-date `dayKey()` for `Asia/Taipei`. Getting this wrong silently files a morning dose under yesterday; the frontend already hit this bug once and documents it.
- **The LLM (OpenAI `gpt-4o-mini`, `functions/src/llm.js`) is the project's only LLM, and it never answers medical questions.** `understandMessage()` returns `{intent, items}` from **one** call — intent classification and medication extraction are two fields of the same structured output, so routing costs nothing extra. `nlu.js` returns `{status:'intent', intent}` for anything that is not `adherence-report`, and `webhook.js` routes it to an existing feature (藥箱／回診／預約／說明／不適) or to `OUT_OF_SCOPE`. Drug-knowledge questions ("能不能配葡萄柚") are classified `other` and answered with "請詢問醫師或藥師" — the same line the DDI engine draws by being rule-based rather than generative: the system does not make medical judgments. Before this layer the model was only ever asked "which drugs are mentioned", so every other question fell through to a generic "我不太確定您的意思" even when the feature existed.
- **Do not widen `MIN_CONFIDENCE_AUTO` (`nlu.js`, 0.8) to make the bot "understand more".** That threshold governs how sure the system must be before writing to a medical record that by design cannot be deleted. Breadth of understanding belongs in the intent layer, not in the write threshold.
- **Reply vs push is a cost decision, not a style one**: LINE bills push messages (200/month free) and explicitly does not bill Reply API. User-initiated flows (link code, 藥箱 query, adherence acknowledgement) must use reply; only the daily card and DDI alerts use push. Swapping one for the other silently changes the monthly bill from NT$0 to four figures.
- **Idempotency uses `create()` as a lock** (`line_push_log`), not read-then-write — retried scheduler runs would otherwise double-push. On push failure the lock is released so a later run can retry.

## Deployment

See `DEPLOY_CHECKLIST.md` for the full pre/post-deploy procedure — it is detailed and encodes real incidents (e.g., `.git/` accidentally served publicly because `**/.*` doesn't match files *inside* a dot-directory; a Cache-Control mismatch between new HTML and cached old JS taking down the whole site after deploy). Key points if asked to deploy:
- `firebase.json`'s `hosting.public` is `.` (repo root) — anything not in the `ignore` list gets uploaded. Never add new sensitive/internal files without also adding them to that `ignore` list.
- `firestore.rules` and the app code are **coupled and must be deployed together**: `firebase deploy --only firestore:rules,hosting`. Deploying only one side silently breaks functionality (old rules reject new collections; new rules reject old code's writes) — see checklist §2 for the exact failure table.
- `tools/delete-user.cjs` is a manual GDPR/account-deletion helper that shells out to `firebase firestore:delete` per known document path; it is not exhaustive (some collections require manual Firebase Console cleanup, noted in its own output) and does not delete the Firebase Auth account itself.
